## 3. 用户最小链路与复用方式

**选择合同倒查 → 上传总包和分包并确认归类 → 点击“开始核查” → 智能核查及事件时间线 → 自动保存报告 → 查看/定位/导出。**

只显示三个用户阶段：上传资料、智能核查、审查报告。无需额外“申请报告”、逐条复核或审批操作。运行后回看资料只读；修改合同创建新的运行版本，原材料和报告保留，不使用准入补件作废逻辑来隐式改历史。

推荐在现有页面增加明确的模式配置与数据适配层。复用页面骨架、材料台账、预览、进度及事件呈现、报告容器；准入与倒查各自负责启动API、业务状态和结果投影。不复制整套页面，也不把整个准入WorkbenchStage控制器强行当成公共引擎。

## 4. 双合同门槛与响应

首版处理“一份总包合同来源集 + 一份分包合同来源集”。分册、附件和补充协议可属于对应来源集；不将多份无关分包混成一个合同，不按文件名或上传顺序猜配对。

1. 总包至少一个有效PDF来源，分包至少一个有效PDF主合同来源；专业/劳务类型归入分包，不要求资质、人证、社保。
2. 多文件复用现有总包来源集及分包主合同/附件关系；仅有两个同角色文件不能满足双合同门槛。附件不能代替主合同。
3. 前端显示可执行原因，后端受理前独立复查角色、归属、解析状态、替换状态和来源关系；缺任一侧即不创建核查作业，禁止直接API绕过。
4. 上传中、解析中或整份文件读取失败，不能当成有效输入。普通解析能力继续沿用，本阶段不扩展OCR专项，也不把OCR噪声及技术指纹写回业务报告。
5. 启动时冻结两侧材料ID、角色、哈希、版本、来源集和关系，以及模型、提示词、依据版本。运行期间不可静默换文件或用新配置接续旧身份。
6. 核查前验证项目/标段、两级主体、工程范围关系；“总包承包人=分包发包人”是重要线索，不是唯一匹配标准。已明确错配不得开展正常衔接比较；关系不足不自动判匹配、不制造违法结论，保留对应未完成状态及已有有效结果。
7. 旧单合同任务及报告继续可读、可导出，不因新门槛消失；新建或新发起的双合同运行按新契约受理。历史失败恢复如需改变输入，应建立新运行身份，不混用旧检查点。

## 5. 核查范围与进度语义

后台依次完成：两侧合同整理及关系识别 → 分包文本/内部一致性与适用规范、负面清单检查 → 适用上游要求抽取和总分包比对 → 证据校验、去重、收尾并保存报告。正文与规范的现有分批能力继续使用，不因为新增总包而取消规范检查。

总包是上游合同约束证据，不是法规。提取质量、安全、工期、工资、检测、保险、材料设备、计价等与该分包有关的约定，区分业主保留、总包自履行、可传导及分包承担；考虑通用/专用、优先顺序、补充协议和例外。

每项比较基于相同对象、责任主体、范围和计价口径。用词/付款比例不同不自动构成不符合；合同概括引入总包条款不等于遗漏。未找到对应条款只说明待核，只有明确适用要求且充分检索后，才能提出约定遗漏风险。总包独立全面审计不纳入本期。

页面展示业务阶段及当前活动，必要时展开“分包正文已完成X/N批”“规范扫描X/N批”“上下游比对X/N批”，明确单位。不得将0/6批称为六步核查；不能靠平均百分比掩盖失败。只有结果验证与报告保存完成才显示完成，任务执行完成和依据适用覆盖分别统计。

无需人工点复核不等于免除服务端自动校验。规范/检索失败、比较未执行、模型异常与零发现各自记录，不能以“报告已生成”宣称全范围已完成。正常完成与部分结果在页面以简洁状态区分，不向报告正文重新塞入用户已要求去掉的OCR说明、指纹、导出时间等技术内容。
