## 3 当前实现与新模板的关系

以下保留需求分析阶段的源码基线，不以历史交接的完成状态代替当前实现；其中“需要调整”“待确认”由第 1.1 节及实施验证记录说明本轮落实情况。

| 对象 | 当前实现 | V1.3 需要的调整 |
| --- | --- | --- |
| 现行正文 | `report_document.py` 的 `bs.business-report-document.v2`，五阶段关键点摘要；`ReportView.jsx` 展示同一投影 | 独立新增 V1.3 文档投影及渲染分支，旧投影和默认行为保留 |
| 八类业务模块 | `business_report.py` 已有八个同名业务维度，另含基本信息与结论，共十模块 | 可复用命名和部分来源映射，不能直接把模块 `available` 当成“维度符合” |
| 模块覆盖状态 | 当前 `available` 主要根据是否有 items，`partial/not_covered` 表示来源不足 | V1.3 必须另行核对适用要点、执行覆盖、读取状态、依据和人工意见 |
| 基本信息 | `reporting.build_report` 已投影项目、标段、总包、业主、分包人、类型、范围、金额、基准日 | 可复用；项目部名称、事项短名、报送日期、发文方等缺少独立可靠字段 |
| 旧意见书建议 | `derive_opinion_conclusion`、`derive_advisory_conclusion` 已存在按三态计数生成建议的逻辑 | 这是旧链路的建议，不能用作 V1.3 已确认的人工审批意见，也不等于人工已批准 |
| 现行判定 | `_point_verdict` 有有限已确认不符合规则；明确注释 hit／severity 不能单独推出“不符合”或“基本符合” | 新维度判定应保留事实和规则边界；“基本符合”的具体可自动适用场景仍待业务确认 |
| 规则策略 | `report_policy.py` 已有独立版本、内容哈希及冻结快照 | 报告模板身份与判定策略身份分别记录，不把更换版式等同于切换规则 |
| 页面与导出 | 页面、Word、PDF 消费业务文档；历史版本使用快照 | 新模板需覆盖相同入口，记录模板及映射版本，历史不自动换版 |
| 报告门禁 | 已有任务级 readiness、人工处置及范围限制规则 | 模板选择沿用当前门禁；能力未覆盖、可选总包缺失不能借模板转换成新的硬阻断 |

### 3.1 当前能力对八维度的支撑

| 维度 | 可复用来源 | 现实缺口与本轮建议 |
| --- | --- | --- |
| 1 分包合规性 | 负面清单、转包／违法分包、签章审批链、A1 依赖规则 | 清单召回不等于全量覆盖；可选总包缺失按已有来源限制披露，不直接判不符合 |
| 2 分包人资格与信用 | 主体证照、资质文字匹配、有效期、内部信用材料 | 等级规模、官方验真、外部信用查询覆盖不足，不能笼统写“信用良好” |
| 3 人员履约能力 | 名单／岗位、逐人证据、劳动关系和社保、证件对应 | 逐人事实不等于所有岗位适用规则已完成；总工是否必需 B 证不能照抄样例 |
| 4 设备与资源 | 材料台账可提供线索 | 既有业务模块没有独立 source kinds；未见完整设备数量、权属及配置规则，先披露未覆盖 |
| 5 分包合同条款 | 合同字段、合同语义、金额和工程量相关规则（以实际执行为准） | 合同字段提取不等于合同条款审查完成；不能只因有合同就判符合 |
| 6 质量安全与进度 | 部分 A1 责任／依赖条款 | 缺少完整方案、措施、进度的专门覆盖；不能挪用“人员证过期”支撑全部维度判定 |
| 7 资金与支付风险 | 部分合同支付信息可作事实线索 | 既有模块无独立 source kinds；缺少完整账户、支付和低价风险规则，先披露未覆盖 |
| 8 农民工工资保障 | 内部材料和部分劳动材料 | 内部信用核查不能替代工资专户、代发、考勤和工资支付核查，需逐要点确认来源 |

结论：八行表格可以新增，八个维度已完整核查不能据此成立。第一版应真实展示现有能力和边界；若要求八维度全部自动判定，需要另立规则能力任务，不能隐含在模板改造中。

| I10 | 责任角色／责任单位 | 样例“承包人／分包人”仅作示例；需要责任依据或人工填写，未知显示待明确，不默认全归分包人 |
| I11 | 补正期限 | 附件若保留则人工填写；不从“限期”自动生成天数或管理决定 |
| I12 | 复核销号状态 | 复用真实人工回执及补件新代；“已采纳”不等于“整改完成”，不能仅由模板制造销号流程 |

普通提示可在“提示事项”中展示；未覆盖／外部未查询可在“核查边界”中展示。三者可以都在附件二分区呈现，但必须带类型，不能混成同一类确定缺陷。

### 4.4 总体意见 补充说明与签字

| 编号 | 字段组 | 来源及处理要求 |
| --- | --- | --- |
| C01 | 符合项摘要 | 来源是有依据的已核查结论；明确统计按事项还是维度 |
| C02 | 待核实项摘要 | 来源是确需核实的事实或证据，不混入所有未开展能力 |
| C03 | 不符合项摘要 | 只接受已确认规则／有权限人工结论，不以预警数量替代认定 |
| C04 | 缺项清单 | 只指证据足以确认缺失的适用材料；缺件可与不符合／待核实重叠，不作为第四种互斥判定相加 |
| C05 | 客观核查总体摘要 | 汇总本次覆盖、问题、提示和限制；范围不完整时不得写成完整通过 |
| C06 | 人工审批意见 | 已确认由人工填写；无意见时显示“待人工审批”或保留空白，不替人作出批准／拒绝 |
| C07 | 补充说明与审查方法 | 自动说明实际文本比对、规则校验、AI 辅助和人工复核；没有原件回执不得写已核验原件 |
| C08 | 审查人／复核人／签发人 | 默认保留空白签字位；登录账户和普通 finding 审核人不能自动替代三类签字 |
| C09 | 人工签署时间 | 有签署事实才填；不是 generated_at 或导出时间 |
| C10 | 附件目录与交叉引用 | 与实际输出的附件一致；正文问题与附件二数量／编号可回查 |
