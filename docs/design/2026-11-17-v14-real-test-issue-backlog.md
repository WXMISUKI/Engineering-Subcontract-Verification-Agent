## 0 一句话结论

当前 V1.4 报告不像领导样例，根因不是排版，而是**把“未核实/无证据/匹配失败”的内容都当成了问题**。报告要像样例，必须先把“已核实事实、确证问题、待核实事项、能力未覆盖”四类分开，再重写正文；否则只是把错误清单排得更整齐。

## 1.1 三篇样例的共同点

| 共同点 | 三篇样例表现 | 对 V1.4 的要求 |
| --- | --- | --- |
| 函件式 | 标题 → 抬头/项目信息 → “经核查……意见如下” → 主题段落 → 结论/要求 → 签章 | 不要做成“问题数据库导出” |
| 主题稳定 | 资质与主体、安全生产许可、人员配置/持证、分包范围/负面清单、合同与计价、结论/要求 | 章节按这六类重组 |
| 结论位置 | 样例 1/3 在末尾，样例 2 开头摘要 + 末尾签批 | V1.4 末尾放“审查结论 + 要求 + 签章” |
| 结论性质 | “原则同意/附条件同意/同意”，是审查主体结论 | 不写“系统建议结论”；系统只给核查结果 |
| 问题呈现 | 问题嵌在段落里，用“注意/但/须/未”标出 | 正文不单独列“判定理由”列 |
| 事实具体 | 证书号、有效期、社保月份、金额、资质等级、人员姓名 | 报告要有已核实事实，不只写“缺 XX” |
| 补正具体 | 补安许、补合同、补社保、补设备、明确关键工序 | 补正要求要能直接执行 |
| 签章 | 建设单位/指挥部（章）+ 日期 | 增加建设单位签章位 |
| 附件 | 三篇都没有 8 表附件 | 8 表是新增需求，放附录，不改变正文函件风格 |

**结论**：V1.4 应按“函件式审查意见”重写，而不是继续优化问题表。8 表附件保留，但只作为附录。

## 2 报告问题（先处理）

### R-01 报告页按钮和区域重复（已修代码）

**现象**：页面同时出现“正式意见书 + 生成正式意见书”和“审查报告 + 导出 Word/PDF”，V1.4 下还有两套导出入口。

**处理**：
- V1.4 下隐藏“生成正式意见书”；
- 只保留一个“正式审查意见”区域，内含“导出 Word / 导出 PDF”；
- 不再渲染重复的“审查报告”导出组。

**代码**：[ReportView.jsx](file:///c:/project/nanjin/Engineering-Subcontract-Verification-Agent/frontend/src/plus-ui/blockchain-supervision/components/ReportView.jsx#L420-L450)

### R-02 报告不是“审查意见”，是“缺项清单”

**现象**：24 行问题表几乎全是“报审资料缺「XX」”，没有样例里的“资质与承接能力、安全生产许可、人员配置、合同与支付、结论”叙述。

**原因**：V1.4 直接用 `findings` 投影，而 `findings` 只记录异常；没有“已核实事实”层。

**处理**：
- 正文增加“已核实事实”段：已提供的证照、已匹配的人员、已核对的社保、已确认的资质范围；
- 问题表只保留确证问题；
- 结论前增加“审查范围与方法”说明。

### R-03 结论与问题不一致

**现象**：13 项缺项 + 3 项不符合，结论仍是“附条件同意”。

**原因**：结论只按“是否有不符合/缺项”粗判，没有区分关键证照缺失与一般资料缺失。

**处理**：
- 关键项（营业执照、资质、安许、发包人书面同意）缺失 → 不能“附条件同意”；
- 一般资料缺失 → “待补正”或“附条件同意”；
- 结论规则要可解释，写进报告边界说明。

### R-04 8 表附件大量 R4，像“空表”

**现象**：表 3–6 几乎全部是“R4 本版本未建立该审查项的自动核查规则”，20 多行重复。

**处理**：
- 每个表顶部只写一次“本表未覆盖事项统一说明”；
- 表内 R4 行简化为“— / 未覆盖”，不再重复长句；
- 有能力但无结论的项用 R10，与 R4 分开。

### R-05 补正要求全是同一句

**现象**：所有缺项都写“请结合问题描述核对合同及相关资料，完成整改后重新核查”。

**处理**：
- 按问题类型生成具体补正：缺营业执照→补营业执照；缺社保→补近一个月社保；缺签字→补签字页；
- 复用每条 finding 的 `missing.labels` / `evidence`，不要用通用句。

### R-06 规则依据没有来源

**现象**：只写“《2025 分包报审附件要求》①9/②9”，没有文件版本、页码、条款原文；用户问“法定签字链/集团报审签字链”从哪来。

**处理**：
- 依据格式统一为：`文件名称 + 版本/文号 + 条款/附件项 + 页码/定位`；
- “法定签字链”“集团报审签字链”必须注明来自 `signature_chains.json` 的链定义及其原始附件；
- 报告不出现“报审资料包”这种内部术语，改写为具体文件名/材料名。

### R-07 标题与描述重复

**现象**：“主要管理人员名单及联系方式：报审资料缺「主要管理人员名单及联系方式」……”。

**处理**：
- 标题做摘要，描述写事实；
- 或描述不再重复标题，直接写缺什么、在哪、影响什么。

### R-08 OCR 问题重复且无定位

**现象**：多处“部分页面识别不完整/未确认”，没有页码和具体内容。

**处理**：
- 全报告只保留一条 OCR 质量汇总；
- 列出受影响材料、页码、影响的问题编号；
- 不再把 OCR 问题作为独立问题逐条重复。

### R-09 无法核实项被当成问题

**现象**：转包、违法分包、负面清单等“不可判定”项进入问题表，用户误以为是阻断项。

**处理**：
- 问题表只放“不符合/缺项”；
- “待核实”单列“未形成确定结论事项”，明确不计入不符合；
- 没有证据的转包/违法分包/负面清单项，不进问题表。

### R-10 正文没有“要求/签章”

**现象**：样例结尾有“要求 ①–⑤ + 建设单位（章）+ 日期”；当前只有审查人/复核人/签发人。

**处理**：
- 增加“后续要求”段；
- 增加建设单位/指挥部签章位；
- 审批意见、期限、签字继续保持人工填写。

### R-11 未展示已核实事实

**现象**：报告只写缺什么，读者不知道哪些已经确认。

**处理**：
- 每节开头写一句“已核查通过：……”；
- 只写有证据的项，不把“未见异常”写成“符合”。

### R-12 结论卡数量口径不清

**现象**：“不符合 3｜缺项 13｜待补正 22”没有说明统计单位。

**处理**：
- 结论卡注明“按机器逐项记录统计”；
- 缺项与待补正不重复计数；
- 与附件二/第九部分同源。

## 4 报告与三篇领导样例的差距

| 维度 | 领导样例 | 当前 V1.4 | 差距 |
| --- | --- | --- | --- |
| 体裁 | 函件式审查意见 | 结论卡 + 缺项清单 | 缺少“审查意见”的叙述感 |
| 结构 | 资质/安许/人员/范围/合同/结论 | 依据 + 7 节 + 24 行问题表 | 结构有，但内容被问题表淹没 |
| 事实 | 具体证书号、有效期、社保月份、金额 | 主要是“缺 XX” | 缺少已核实事实和具体数值 |
| 问题 | 嵌在段落里，少量 | 24 行表格，大量重复 | 问题颗粒度和数量都失控 |
| 结论 | 原则同意/附条件/同意 + 条件 | 附条件同意 + 13 缺项 | 结论与问题不匹配 |
| 要求 | ①–⑤ 后续要求 | 无 | 缺少“要求”段 |
| 签章 | 建设单位（章）+ 日期 | 审查人/复核人/签发人 | 缺少建设单位签章位 |
| 附件 | 无 | 8 表，多为 R4 | 附件没有形成有效补充 |

**结论**：V1.4 的骨架方向是对的，但当前内容层是“问题数据库导出”，不是“审查意见”。需要先做事实分层和问题抑制，再谈措辞。

### 第一步：报告页与问题文本（本轮已做一部分）

1. 去掉重复按钮和重复导出组（已改 [ReportView.jsx](file:///c:/project/nanjin/Engineering-Subcontract-Verification-Agent/frontend/src/plus-ui/blockchain-supervision/components/ReportView.jsx#L420-L450)）。

4. OCR 问题聚合为一条。
5. 8 表 R4 行简化为“未覆盖”，长说明只写一次。

### 第二步：核查准确性（报告能不能信）

1. C-16 证照缺失误判：修材料分类/证照识别。
2. C-14 社保匹配：修参保人员表解析。

### 第三步：报告叙事重写（像样例）

1. 每节写“已核实事实 + 确证问题 + 待核实事项”；
2. 增加“后续要求”和“建设单位签章”；
3. 结论规则区分关键项与一般项；
4. 8 表附件与正文同源，不重复长句。

### 第四步：复核区交互

1. 去掉顶部上传/补件按钮；
2. 修最后一条处理完不回列表的 bug；
3. 问题详情返回列表时保留筛选和位置。

## 7 仍需确认

1. 关键证照（营业执照、资质、安许、发包人书面同意）缺失时，建议结论用“不同意”还是“待补正”？
