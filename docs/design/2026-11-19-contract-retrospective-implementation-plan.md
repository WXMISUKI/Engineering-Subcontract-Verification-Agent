## 1. 目标与现状

用户链路：选择合同倒查 → 上传分包合同（总包可选）→ 开始核查 → 后台执行 → 自动保存报告 → 查看原页或导出。无需逐项人工确认，无需另点生成报告。

阶段1已完成：任务模式保存、默认准入兼容、顶栏入口、创建后锁定及恢复。阶段2技术闭环已完成：独立结果/运行契约、逐页跨页索引、适用依据筛选、原文及时效验证、持久后台任务及恢复、自动报告、独立页面、原页入口与基本Word/PDF导出。隔离上传至导出、模拟模型、真实文本离线回放与PDF视觉检查已通过。真实Provider分析质量、实际浏览器全链路、Word人工视觉检查及业务专家验收仍留阶段4，不冒充完整试用验收。阶段3总包辅助尚未开始。

当前工作区还保留未提交的安全费专项。实施倒查时保留这些改动，不依赖其中未验收能力；必要的共享修改按具体差异处理，禁止清空工作区或整体覆盖。

## 2. 已确定的业务边界

- 对合同文字及其适用依据提出文本不符合、内部歧义、条件性风险、上下游衔接风险和现行提示；不核验实际履约、不要求资质/社保等准入证明材料。
- 首版一个分包合同来源集、至多一个总包来源集；附件与补充协议明确归属。项目、范围、主体或版本不可靠时不强行配对。
- 历史判断与现行提示分别表达。日期、效力或适用条件不明时保留限制，不能用今天的规定直接定性旧合同。
- 总包为上游合同约定来源，不是法规范；区分业主保留、总包自行承担、可传导及分包具体承担的责任。
- 原文摘录不润色。风险说明采用“约定事实 → 存在的差异/适用条件 → 风险含义”的专业表达；不编造整改期限、审批命令或实际发生的行为。
- 用户可直接阅读系统辅助分析报告。自动出报告不表示系统已证明全部条款合法，也不强制增加人工逐项确认流程。

原清单把自动报告集中放在阶段4。用户已确认将其最小能力前移到阶段2，让每个主要阶段都有完整可用链路；沿用阶段编号并已同步 OpenSpec。

| 阶段 | 交付物 | 完成条件 |
| --- | --- | --- |
| 0、1 | 已冻结方案和任务模式 | 已完成，本次不重做 |
| 2 单合同最小闭环 | 单份分包合同可后台审查、自动保存八列表报告、原页查看与基本同源导出 | 用户不进入准入补件/逐项复核流程，刷新后可读同一报告；缺依据/读取失败如实显示 |
| 3 总包辅助闭环 | 在阶段2上增加匹配上游要求及双侧比较 | 有无总包自适应；衔接发现有双侧证据，错配合同不比较；基本报告和导出继续可用 |

## 4. 技术路线

复用现有上传、OCR逐页来源、合同抽取、模型客户端/用量、依据快照、后台作业、事件与报告导出能力。新增倒查专属编排与结果契约，以模式分支接入；准入规则及其人工门禁继续独立执行。

现有 `service.run_semantic_checks` 调用 `semantic_review.compare_contracts` 后保存待人工确认候选，因此只能复用分块、调用和证据校验等适合部分，不能直接删除“待人工确认”文案作为倒查实现。

建议数据流：

1. 接受任务时锁定合同文件哈希/角色/版本、模式、模型身份和依据版本；同次运行中不因部署默认模型切换而改变分析身份。
2. 基于逐页读取结果建立条款索引，跨页条款保留来源；附件、通用/专用、补充协议关系明确后再确定比较对象。
3. 按已登记的审查主题与适用依据召回检查，不按“先找出几个问题”驱动。明示可检查范围，并记录各主题执行、受限或不适用情况；不会默认为已覆盖全部56条。
4. 单合同分别检查适用规范冲突、内部矛盾/歧义、金额日期和引用一致性、有明确适用要求的约定遗漏。具体内容由合同触发，不输出空泛全量清单。
5. 模型生成结构化候选和专业说明；服务端校验材料、物理页、真实摘录、依据版本/时效、适用条件及比较关系。来源校验通过不等于适用判断必然正确，条件不足降为条件性风险或范围限制。
6. 去重、合并同一事项的多处来源，保存经过校验的发现及覆盖情况，再自动保存报告。报告展示/导出读取同一份已保存内容。

首版不新增必需的“润色模型调用”。在分析输出契约中明确专业表达规则；如后续确需摘要润色，只允许消费已校验事实，不可改原文、增减事实或改变问题性质。导出、刷新不触发付费调用。

发现字段至少包含：类型、时间口径、合同角色/主体、文件及版本、条款编号/标题、PDF物理页、原文片段、风险说明、依据和适用条件、关联发现/来源、运行身份。

内部歧义以同合同的两段约定作为对照来源；上游衔接以总包条款作为合同依据。不能为了填满依据列而虚构法条。确定性规范不符合必须另有可核验且适用的规范依据。

存储优先复用现有运行/报告快照，并给倒查结果明确的 schema 版本；后台复用已有作业事实源、租约及恢复机制。具体存储接线在阶段2首个小任务核定，不为此复制另一套作业框架或提前引入新依赖。

## 5. 阶段2具体任务与依赖

每项完成更新验收台账，阶段完成向用户汇报“做了什么、验证了什么、未完成什么”。普通任务间自主衔接，不反复请求已确认的业务授权。

| 任务 | 内容与可能涉及区域 | 验收/验证 | 依赖 |
| --- | --- | --- | --- |
| 2.1 运行与结果契约 | 新倒查结果/运行契约；核定现有快照和后台接点；补 OpenSpec 场景 | 清楚区分发现、限制和执行失败；覆盖旧任务默认准入、结果序列化与身份稳定的隔离回归 | 方案确认 |
| 2.2 合同输入与索引 | 模式化上传适配、合同来源集、逐页/跨页条款索引；复用当前解析模块 | 仅分包合同即可形成可核查输入；未读页/未关联附件不当成条款遗漏；跨页来源可回指 | 2.1 |
| 2.3 依据选择与分析 | 新单合同编排/提示词；复用依据登记与模型调用 | 按主题有覆盖记录；历史/现行分离；内部歧义与明确规范要求可生成候选；无依据不硬判不符合 | 2.2 |
| 2.4 校验与报告投影 | 原文、页码、依据与适用条件校验；去重；专业说明和八列投影 | 伪造引文/日期冲突/无前提定性被拒绝或降格；原文不被润色；有效发现与限制分开 | 2.3 |
| 2.5 后台自动保存与API | 模式分流、复用作业/事件/用量、保存运行及报告快照 | 重复启动不产生重复运行；离开/刷新不取消后台；恢复不重复已完成调用；报告自动保存 | 2.4 |
| 2.6 页面与基本导出 | 倒查上传说明、运行状态、表格报告、原页入口；复用现有导出渲染 | 不进准入复核队列；正常/部分/失败/零发现可区分；页面与Word/PDF读取同份保存结果；离线及必要浏览器检查 | 2.5 |

2.1—2.4先以现有只读文本和模拟模型验证；不提前去掉启动保护。2.5—2.6接通后再替换保护，并在隔离环境验证可用链路。正常完成、部分受限均可自动保存各自状态的报告；完全未执行只显示失败及原因，不能形成“无风险”报告。

## 6. 阶段3和4任务

阶段3顺序：总分包关联/范围匹配 → 上游责任及例外提取 → 适用条款配对 → 双侧发现校验 → 同源页面及导出 → 正反例回归。总包未上传时跳过比较，单合同结果不受阻。

阶段4顺序：核对样本与已有文本 → 在隔离库/上传目录完成全链路 → 真实模型输出验收 → 浏览器与Word/PDF检查 → 准入/历史回归 → 汇总可试用范围。若真实模型发现明确缺陷，修复后仅针对受影响范围复验，不循环追求固定发现数量。

真实Provider验证前明确单次文件范围、调用/费用上限和停止条件，沿用已批准的范围；本方案不自行假设无限调用授权。原件或已有OCR不可靠处标明限制，只对必要页有界补读。

## 7. 验收样例和不应误报的情况

| 情况 | 期望 |
| --- | --- |
| 分包第39物理页12.1费用/延期前后约定 | 可列内部歧义，并给出相应两段原文，不自动宣告无效 |
| 总包检测由招标人另委托，分包写试验检验费承担 | 核范围是否同一、是否只是配合费；成立时提示边界风险，不能只看用词不同 |
| 总包由业主投保，分包有条件式分担约定 | 区分险种、投保和费用责任，不要求重复购买所有险种 |
| 总包85%、分包80%付款 | 不能仅凭比例差异认定违法 |
| 2023签约、2024生效规则 | 不直接据此认定签约时不符合，现行提示另列 |
| 合同出现“箱梁” | 不自动推断整孔预制梁或满足负面清单的全部条件 |
| 错项目、不可读页、模型/依据失败 | 单独呈现受限范围或失败，不制造缺社保/资质待办，不写全部合规 |
| 完整执行后零发现 | 表述为本次已覆盖范围内未发现可列示问题，允许正常自动保存报告 |

这些是验收命题，不是预先认定样本确有违法；发现数量不作为成功标准。
