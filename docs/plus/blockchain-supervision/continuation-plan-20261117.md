# 工程分包独立版后续阶段任务方案

日期：2026-11-17
依据：`standalone-learning-progress-review-20261116.md`、`standalone-platform-learning-governance-20261115` OpenSpec、`bs-review-contract.v1` 交叉表、`stage-2-gap-analysis.md`、V1.3 内容修订验收记录及当前工作区状态。

本文把前期讨论的差距整理成一个可分阶段验收的执行顺序。它不替代已冻结的业务契约，不表示真实材料、专家验收、客户迁移或部署已经完成。

## 已冻结的方向和约束

- 独立版优先；智能体广场版适配暂缓。两仓保留本地 DTO/schema，以版本化 OpenSpec 和应用适配器承载契约，暂不抽共享代码包。
- 阶段 2 的首批范围采用方案 A：报告/收口最小任务级门禁前置，再实施 4、5、13、25 与 21、24 对应切片。用户未授权客户数据库迁移或部署。
- `finding_semantics` 为可空字段。历史 `NULL` 保持旧门禁语义，不推测回填。
- OCR 读取质量用于披露和提示，不单独阻断报告生成/收口；真实任务执行失败、必需范围未完成、身份/范围冲突仍须按原门禁处理。本阶段不重跑 OCR、模型或核查规则。
- V1.3 与旧模板并存，旧版默认。V1.3 当前先支持单主体；人工审批意见、期限和签字在导出 Word 后填写。
- 任务 7 已由用户确认业主为“上海沪申高速公路建设发展有限公司”，该事实只属于任务 7，不能作为其他任务默认值。
- 真实报告的字段与编排修订已实现并交给用户验收。旧核查结果中仍列缺项或证据不足的项目，不因字段补全或换模板自动改成符合。
- 保留当前分支和所有未提交改动；不 reset、clean、stash、提交或推送，不操作 8089/客户/线上环境。

## 阶段方案

### 阶段 A：完成当前报告验收与阶段 2 收口（当前）

范围：先由用户检查任务 7 的 V1.3 报告，再对已经批准的 A0–A6 切片整理有限、只读的代表性验收证据。只使用已有任务快照、页面和导出；不重新 OCR、调用模型、运行新核查或改写人工回执。

主要问题：

- V1.3 内容和格式是否符合领导模板与业务口径；基础字段、依据去重、八维度四列表、正文分类概要、附件二五列主题归并是否足够。
- 普通人工提示、机器无法判断、未执行/失败和真实阻断事项在任务门禁、API、工作台、Word/PDF 中是否一致。
- 负面清单候选及覆盖是否与执行失败区分；监理和发包人证据是否双侧可追溯；人员/社保证据是否逐人而不跨主体；质量归组是否不共享 finding 或回执。
- 如报告用户验收提出问题，只修复可由现有事实/投影证明的问题；不得借报告修复重跑核查并改变业务结论。

完成条件：报告业务验收结论有明确记录；已批准的首批差距逐项标注源码、回归、隔离材料、真实材料、专家验收证据等级；OpenSpec task 3.4 有结论。之后请用户确认阶段 2 结果，再进入页级闭环。若用户报告尚未检查，则此阶段停在“待用户验收”，不代用户打勾。

### 阶段 B：页级人工复核闭环规格与决策

依赖：阶段 A 收口并获用户确认。

先定义页级动作和边界：查看原页、确认可读/不可读、重读、补件；动作绑定材料修订、物理页、任务/主体、核查代及证据来源；说明何种变更使回执失效，以及人工确认不等同于合规结论。明确权限、审计、并发与重试语义，兼容历史无版本数据。

验收物：OpenSpec 场景与数据/API/UI 状态图；包含旧快照、替代材料、未读页、执行失败、并发回执和补件后的失效反例；经用户确认方案后才实现。若需新增/变更持久化 schema、数据迁移或外部 OCR 行为，单独列影响与回退，实施前再次确认。

### 阶段 C：页级闭环逐切片实现

按“持久化与版本/权限 -> API -> 单页工作台动作 -> 后续核查与报告投影”顺序做垂直切片，每个切片单独回归后再进入下一项。

完成条件：用户能定位原页并执行批准动作；材料修订或核查代变化时旧回执按规则失效；未读、未覆盖、运行失败与人工确认保持可区分；历史快照只读且不被当前材料重建；报告不把人工确认误写成自动符合。

### 阶段 D：报告与任务门禁跨形态一致

依赖：阶段 C 的页级状态契约稳定。先复核现有 `bs-report-adaptation`、报告门禁和 V1.3，不复制第二套投影逻辑。

核对当前旧模板与 V1.3 页面、API、文本预览、Word、PDF 的版本来源和事实一致性；覆盖范围未覆盖、AI 未完成、执行失败、待读复核、OCR 质量提示与真实阻断等组合；检查草稿导出与正式文件/收口门禁的差异。真实代表性材料及人工处置须由用户授权并由业务人员验收，模型建议数量和合成结果不能替代。

完成条件：各入口使用一致的任务就绪判据；多格式输出可追溯到同一任务/版本/映射；历史版本冻结；无论旧模板或 V1.3 都不会将 OCR 提示升级为门禁，也不会将必需执行缺口降级为普通提示。

### 阶段 E：其余规则差距候选与业务口径复核

只在首批验收完成后开展，按垂直切片和用户确认顺序推进：

- **签字链与时序：** 已发现“仅有日期是否被当成签署”“组内仍有未读页时全节点路径如何判定”等待验证反例。先构造失败回归并确认是否为真实缺陷；按同主体/同范围配对，不混合格式，也不以静态风险直接宣称线上缺陷。
- **主体与系统外事实：** 明确材料内证据与外部履约事实边界；多候选不择一，不跨合同链拼接；外部事实缺失保持人工提示，系统执行失败另行表达。
- **合同范围与多方关系：** 先锁定主体、项目/合同段和完整合同链证据。资料不足、主体冲突或未读与规则未命中严格区分，不迁移平台专属例外或未确认占比规则。
- **13 条待确认意见：** 保持待确认队列。逐项说明选择会改变的业务结论、所需证据和推荐方案，一次只讨论改变实施范围的决定；没有确认不进入业务规则代码。
- **5 条样例：** 仅保留通用机制，不迁移其中具体人名、日期、结论、项目事实和数值。

每项的完成条件是“口径确认 + 失败反例 + 规则/证据实现 + 定向回归 + 端到端投影 + 对应等级业务验收”，不因代码存在或专家意见来源写着“已确认”而宣称通过。

### 阶段 F：后台恢复与跨形态兼容评估

逐项对比任务代次、事件、租约、checkpoint、重试和计费幂等；列出迁移源、目标 adapter、身份/版本映射、未知状态和回退办法。先证明共同需求及维护收益，之后才讨论抽包；当前“不抽共享包”的决定继续有效，若要改变需用户重新确认。涉及 schema、身份、计费、部署或旧客户端的方案必须单独设计评审。

### 阶段 G：独立交付 P0–P6 验收

依 `standalone-docker-delivery` 分别验收资料/知识链路、隔离账号、完整流程、恢复、镜像与离线包、许可证/密钥边界、提交交接和目标环境。源码测试、隔离候选、真实业务/专家验收、客户部署结论分栏记录。每次客户环境迁移、数据库操作或部署都需要具体目标和单独授权；本方案不构成部署批准。

## 阶段门与执行纪律

| 门 | 继续条件 | 不满足时 |
| --- | --- | --- |
| A → B | 任务 7 报告验收结论已记录，阶段 2 证据分级完成，用户确认阶段 2 关闭 | 继续阶段 A；不开始页级持久化/API 设计 |
| B → C | 页面动作、来源/版本、权限、回执失效和旧快照行为形成规格，架构决策已确认 | 维持只读设计，不改 schema/OCR |
| C → D | 每个切片回归通过，页级状态在 API/UI/版本投影可追溯 | 修复当前切片，不叠加后续工作 |
| D → E | 两模板和多格式门禁一致，报告业务验收结论已记录 | 留在报告门禁阶段，不扩充规则 |
| E → F | 每个采纳差距具备确认口径、反例和业务验收证据 | 保留待确认，不猜测规则 |
| F → G | 映射/恢复方案完成评审；交付清单、环境、回退及授权范围明确 | 不迁移、不部署、不共享代码包 |
