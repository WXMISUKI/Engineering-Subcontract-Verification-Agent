# 第一阶段设计与验收契约

## 1 核心链路

登录 → 上传 PDF → 确认主体 → 启动 → 五组核查 → AI 执行 → 待核实处置 → 收口 → 正式输出。

补件：冻结旧基线 → 编辑及上传 → 重核候选 → AI 执行 → 候选复核 → 收口发布 → 正式输出。解析失败只使候选失败，不能覆盖旧材料或历史报告。

## 2 发布契约

| 状态 | 当前草稿 JSON | 草稿文件 | 正式输出 | 收口 |
| --- | --- | --- | --- | --- |
| 普通运行 | 依只读报告门禁 | 禁止 | 核查、AI 与复核满足后允许 | 同正式技术与复核门槛 |
| 补件候选 | 禁止冒充当前正式报告 | 禁止 | 未发布前禁止 | 当前代核查、AI 与复核满足后发布 |
| 已发布 | 允许 | 禁止 | 依当前代正式门禁 | 重复收口幂等 |
| 候选失败 | 当前输出禁止 | 禁止 | 当前输出禁止 | 修复后重新发起 |

历史版本按既有版本授权读取，不能因新候选失败而被改写。`publication_status=ready` 表示 findings 已准备好供查看/复核；它可以与 `publication_state=candidate` 同时存在，不代表正式报告已经发布。正式输出以 `confirmed_output_ready` 和发布状态共同决定。交接中把 ready/candidate 视为互斥的判断不准确，以当前 router 的实际接口契约为准。

`/complete` 是现有候选发布入口。测试必须先满足执行与复核条件，验证发布前拦截，再调用入口并验证发布后的 generation、version 与输出一致，不通过放宽门禁获得通过。

## 3 合成验证边界

- SQLite 与上传文件均位于 pytest 临时目录；账号、PDF、模型响应均为合成。
- 模型客户端在测试开始前注入；合同双路抽取不连接真实 Provider。
- 合成 AI 完成只证明客户端边界下的流程，不证明真实 Provider、法规正确性或业务材料验收。
- 原失败保留在 implementation-validation.md；正式维护的回归测试保留，一次性诊断材料删除。
