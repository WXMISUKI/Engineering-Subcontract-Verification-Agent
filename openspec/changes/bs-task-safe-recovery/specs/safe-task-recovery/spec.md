# safe-task-recovery

## ADDED Requirements

### Requirement: 恢复操作须由用户主动发起并经过服务端并发校验
系统 MUST 将停滞候选与安全可恢复状态分开处理，恢复操作 MUST 由用户主动发起并在服务端核验审查代、材料与执行状态。

#### Scenario: 回执长时间没有更新
- **当** 用户查看或刷新长时间没有新回执的任务
- **那么** 系统 SHALL 保留已有结果，不得仅凭回执过期自动重跑或判定执行已停止。

#### Scenario: 存在活动或无法核实的执行
- **当** 核查、AI 或其准备阶段仍活动，或者系统无法可靠核实执行状态
- **那么** 系统 SHALL 拒绝破坏性重核查并向用户说明；不得仅通过本地进程状态推断其他实例已停止。

#### Scenario: 请求使用过期审查代
- **当** 用户提交恢复时的预期审查代与当前任务不一致
- **那么** 系统 SHALL 拒绝请求并保留当前和历史结果。

### Requirement: 重核查完整保留历史及其可见性
系统 MUST 在变更现有结论前完整保存旧结论、人工回执及必要字段，且不得绕过受限内容的既有可见性规则。

#### Scenario: 历史保存无法完整证明
- **当** 旧结果包含现有版本快照未覆盖的记录或字段，而系统无法完整安全归档
- **那么** 系统 SHALL 拒绝重核查，不删除或修改旧结论。

#### Scenario: 规则版本不一致
- **当** 用户明确发起恢复且服务器确认可以安全执行
- **那么** 系统 SHALL 保存旧代并建立新核查代，禁止将旧覆盖直接标记为有效。
