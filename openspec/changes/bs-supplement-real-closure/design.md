# 方案 A：补件重核与自动生效

## 用户语义

同一任务保存上次结果、候选材料与候选核查。补件期间用户可查看标记为上次结果的只读基线；新结果经系统检查完整且可供人工处理后自动生效，无需用户确认版本。问题复核、报告收口仍独立执行。历史比较是可选功能。

## 实施约束

1. 在进入补件编辑、上传或修改材料前，以同一事务冻结旧材料、主体、结论、回执、参考及可用报告，指向唯一基线。重复进入不得创建重复基线。原任务或规则版本不完整时，不能伪造完整历史报告。
2. 活动工作集现由 `bs_finding` 与任务选项直接更新；不能声称已支持多版本并行。候选运行和公开读必须有明确分界：基线以冻结快照只读投影，运行中的局部结果不可作为已完成的新版本；基线接口必须验证任务归属和历史依据权限。
3. 候选应冻结材料/主体/规则/审查代指纹；并发改动、旧运行完成、租约丢失或任务被删除时，不得覆盖新运行或将过期结果生效。重复提交必须复用同一补件代或明确拒绝。
4. 以原始材料与有效补件为输入，按影响映射和可验证的来源选择核查范围；不能证明范围时回退到组或全量。读取失败、主体冲突、候选缺项和不安全继承应停止并提示。
5. 候选自动生效与业务任务收口是两个状态：全部所需确定性组终态可核对、AI 辅助状态明确并按既有规则允许人工处理时，系统自动切换展示；仍需人工处理的问题不可误标为已解决或已复核。不能将 `supplement_plan.status=completed` 作为候选生效信号，因为当前仅任务收口时才更新。
6. 受影响项的旧人工意见保留在基线；新结果不能因字段文字巧合相同而盲目沿用。未受影响项仅在材料、主体、规则及相应参考输入均可证明一致时沿用；否则扩大重核并要求复核。材料人工确认独立纳入校验。
7. 当前报告、问题列表、来源页、人工操作必须来自同一有效代；补件处理中及失败时基线只能作为上次结果读取，不可冒充含新附件的当前报告。历史报告不存在时明确提示，不重建伪造。
8. 方案必须先在隔离 SQLite 测试并验证 MySQL 事务语义与迁移兼容；候选设计如需新的持久表/列，则另提供可恢复迁移及回滚，不直接修改现有部署。保留现有 API 契约及其他用户数据。

## 增量与验收

先修补进入补件前快照时序并验证原材料、人工意见、重复调用及并发，再明确公开读取与候选状态的端到端实现，最后做真实材料补件、故障恢复和浏览器验证。每个增量都须保留回归，不将快照时序修复等同完整方案 A。
