# 补件与重核现状梳理（2026-11-06）

## 用户确认的目标

- 同一任务内补件；上一次结果供查看，标明补件处理中或历史状态。
- 新一轮结果达到系统规定的可展示条件后自动作为当前结果，不新增“确认新版本”操作；具体问题的人工复核和确认报告的既有业务门槛仍须执行。
- 历史版本可按需查看、对比，不作为主流程强制操作；证据不足不伪造已解决或符合。

## 已核对的代码现状

1. 工作台的补件入口设置 supplementMode：选文件后创建补件计划、进入补件编辑并上传，材料准备后调用 supplement-rerun；普通材料编辑走另一条 material-edit 路径。来源：`BlockchainSupervisionWorkbench.jsx` 约 305、424、932、1903 行。
2. `plan_supplement_generation` 基于材料类别、条目和主体生成并保存计划；`supplement_impact.py` 采用静态类别到核查组映射，未知类别全量回退，信息不足按组回退。这是范围规划能力，不证明规则依赖表完整。
3. `enter_supplement_edit` 保存父代引用并保留当前 findings，但把任务切回 setup、清空当前参考运行指针。`rerun_task` 在重核激活时先保存快照，再删除实际范围内旧结论并进入 running；各组随后写入新结论。因此尚未实现或证明“新一轮结果准备完成后原子切换”。
4. 普通 `enter_material_edit` 与补件编辑不同：保存快照后删除当前 findings。必须逐入口核对，不能把两种入口视为等价。
5. `_inherit_review` 按主体、条目、材料、页码配对，比较状态、文本、证据等字段后继承或标记失效；这属于既有机制，不能仅凭字段一致就证明所有业务依赖未变。材料人工确认还有独立存储，需要一并审计。
6. 前端有历史版本列表、只读摘要与对比组件，后端提供历史与差异接口；是否能在补件准备、失败、中断、恢复及全部浏览器入口正确查看，尚无本阶段验收证据。历史报告只有快照存在且权限及相应检查通过时才能读取，不能笼统承诺所有历史版本都有报告。
7. 当前报告按当前结果和运行状态守门，历史报告读取冻结快照；核查组齐全、人工意见与确认报告之间的闭环仍需在新生效机制下重新验证。现有补件计划的 completed 是任务收口时更新，不应直接等同于机器核查完成或当前结果自动生效。
8. 合成材料 HTTP 流已覆盖补件、重核、报告、人工处理和收口；使用模拟模型与映射。真实材料线上识别与部分页面定位另有隔离验证，但尚无真实补件闭环或业务专家结论。旧隔离样本的人工回执是技术测试数据，不是业务审核。

## 主要差距与风险

- 同一工作区未证明同时维持稳定旧结果和独立候选结果；当前删除旧结论再分组写入的顺序与方案 A 存在差距。
- 补件主体、材料类型、追加/替换、范围映射与未受影响结果继承需要端到端一致；需要防止旧依据或旧人工意见错误沿用。
- 文件读取、后台模型调用、进程重启和数据库提交跨越多个步骤；重复提交、并发编辑、失败恢复和旧结果/报告展示须明确。
- 现有历史版本号与当前审查代不必然一一对应，须避免在前端或报告中错误标注版本；仅依赖现有最新历史版本号不足以证明当前代身份。
- 未验证真实扫描附件的补件来源、身份归属及跨页定位；不能用模拟文件或其他主体材料冒充有效业务补件。

## 接下来设计与验收

1. 设计自动生效的候选与当前结果状态、输入版本、稳定读取及原子切换；机器处理失败和人工复核门槛分开。
2. 设计补件影响范围与安全回退、追加/替换、主体冲突和人工意见继承规则。
3. 确定最小兼容实现、数据库变更及回滚方案后，先隔离验证，不改原用户数据。
4. 逐层验收异常与并发、接口和数据、真实工作台、真实材料和报告；技术回执不能当作业务确认。
