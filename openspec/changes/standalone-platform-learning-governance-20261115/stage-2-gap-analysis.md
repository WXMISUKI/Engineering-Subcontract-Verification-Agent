## 4. 报告门禁是本次范围选择的关键依赖

当前独立版：

1. `service.report_output_readiness` 与 `_report_output_readiness_base` 允许部分中间结果可读，保护材料/规则指纹、核查代和候选发布。
2. `router._require_current_output_ready` 在输出入口重查 readiness，再查当前 finding 回执；这部分服务端保护已存在。
3. 正式输出与收口判据并非完全同源：`complete_review` 另查分组、后台 AI、覆盖和人工回执。读取完整性参数主要检查解析失败，不能直接当作所有页质量、必需负面清单执行完整性均通过。
4. 当前导出 API 仍接受 `stage=draft`。广场新策略只允许应用内 JSON 草稿，文件预览/Word/PDF/证据包要求正式就绪；这是行为及兼容性变化，不能无确认复制。
5. 当前 `GET task` 没有等价任务级 `report_readiness` DTO。`ReportView.jsx:300` 使用 `blockingByStage` 缓存，工作台收口传入本地 `pendingProblems`；`reviewQueueModel.reportGateForGroups` 只是辅助函数，未检出实际调用，不能据其存在断言所有按钮由该函数控制。缓存意见书按钮亦需定向核验。
6. `reading_gap_scope` 和可选来源策略允许部分范围披露路径；广场新正式输出策略对必需读取/执行缺口更严格。不得把“自愿未启用可选来源”与“已选必需范围未读/未执行”统一硬阻断，也不得把既有范围受限收口直接当新策略已满足。

因此，普通提示不阻断的语义改造与最小正式门禁需要同批规划，否则可能把本应由任务层阻断的问题改成可忽略 finding 后放行。
