## Goals / Non-Goals

**Goals:**
- 先建立公共业务语义与交付形态适配层的映射，再顺序推进规则/证据、页级人工复核、报告门禁、恢复兼容和独立交付验收。
- 每项回学记录来源提交、目标边界、验证映射、未迁移内容和回退办法。
- 保留历史任务、材料事实和人工决定；只读、合成、候选、真实业务及部署证据分别记载。

**Non-Goals:**
- 本变更不创建独立版与平台版共用的代码包，不合并用户表、Cookie、数据库表或账单流水。
- 不迁移广场版全部功能，不引入其他智能体或平台宿主进入独立交付镜像。
- 不重跑/改写历史任务，不连接真实业务材料、外部模型或客户环境；这些动作需对应阶段的单独授权。

## Decisions

### D1. 近期产品与交付方向

采用独立交付优先，平台适配单独排期。评估过的替代方案是立即建设双形态共享核心，或以广场版为主、独立版仅作适配器；前者会在业务契约仍未冻结时引入身份、部署和兼容复杂度，后者与当前目标相反。

### D2. 公共核心先作为契约边界（用户已确认）

用户确认先以版本化领域/API 契约和能力映射表达公共语义，身份、Cookie、数据库初始化、计费、菜单和部署保留在适配层；暂不抽取共享代码包。领域契约由 OpenSpec 管理，只有未来实际建立跨形态 adapter 消息时才携带 contract version；各应用内部 API schema 继续独立演进，本阶段不批量修改 endpoint。只有两边契约稳定且重复实现已有明确维护收益时，再单独评估共享包。直接复制文件或立即抽包均不属于本阶段方案。

### D3. 回学分类

每项能力归为：保留独立实现、回学业务规则/证据反例、通过适配器复用、暂缓评估、禁止直接迁移。对 38 条专家意见逐条映射确认状态、独立版适用性和证据等级；只实现已确认且符合独立版范围的事项。平台身份和账单等事项不得仅因平台已有实现就进入独立版本。

### D4. 阶段与依赖

依次为：方向和范围（已由用户确认）；能力映射及契约冻结；规则与证据质量；页级人工复核闭环；报告投影与门禁；后台恢复及跨形态兼容评估；独立交付 P0-P6 验收。前置阶段未通过验收门时，后续依赖该决定的代码任务不启动。

### D5. 现有任务的唯一来源

上层阶段引用现有 OpenSpec 的任务和验收，不复制其任务状态。阶段完成需要同时满足对应规格、定向技术验证和该阶段所要求的业务/交付证据。

## Risks / Trade-offs

- [映射过早固化] → 来源提交、差异和未决项都记录版本；每次跨仓回学前重新核验。
- [上层计划与功能 OpenSpec 重复] → 本变更只跟踪阶段门和引用，不复制实现清单。
- [把技术成功误作业务成功] → 验收证据按隔离技术、真实材料/专家、客户部署分级记录。
- [契约抽象不足或过度] → 先定状态语义和版本边界，不提前抽取共享运行时代码；后续用真实调用关系和重复维护成本复审。

## Migration Plan

1. D2 已获用户确认；在确认 `contract-crosswalk.md` 的 v1 语义和映射前，不开展依赖该契约的代码改造。
2. 按阶段引用的现有 OpenSpec 推进规则/证据、页级操作和报告门禁，每阶段在规格中记录证据等级与差距。
3. 只有业务语义稳定后，才评估后台状态/事件/计费兼容；如涉及 schema、身份或事实源变更，另行给出方案及回退设计并等待确认。
4. 独立部署、许可证和客户环境验收继续按 `standalone-docker-delivery` 管理；任何部署动作须另行明确授权。
