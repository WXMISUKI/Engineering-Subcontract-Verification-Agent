# 可选来源范围限制与判定闭环设计

## 已确认的业务原则

1. 专业或劳务分包合同是分包核查的启动基础；总包合同为可选上下文。
2. 缺少总包只影响确实依赖总包证据的规则，不影响其他分包规则继续核查。
3. 可选来源缺失不产生 `hit`、`miss` 或 `undecidable` finding；它不是通过、违规或需用户裁决的问题，而是独立的规则覆盖限制。
4. 范围提示可以显示在“待处理”工作区，但必须与 finding 队列分区；不要求采纳/忽略、不计入 finding 数量、不触发 finding 处置门禁。
5. 在其他正式报告门槛均满足时，允许生成明确披露范围限制的报告；报告不得汇总为“完整通过”。真实未完成执行和真实 `undecidable` 仍遵循现有门禁。
6. 补充总包后，只有解析、归属确认和新核查代对受影响规则执行成功，当前范围提示才解除；旧代与历史人工意见保持只读。

## 当前契约与分层

当前 `classify.py` 已规定总包 0/1 份可选、专业或劳务分包至少 1 份；`W16-03`、`V16-02` 已有“跳过需总包原文的规则并在报告说明”的实现模式。其他规则存在缺源转 `undecidable` 的路径，需以规则来源矩阵为准逐项收敛。

不得混用以下状态：

| 概念 | 含义 | 示例 | 是否是 finding |
| --- | --- | --- | --- |
| 来源状态 | 某类材料当前提供和读取情况 | 未提供、处理中、可读、终态不可读、归属冲突 | 否 |
| 规则适用性 | 规则是否适用于本主体/任务 | 适用、不适用、待基础事实确认 | 否 |
| 执行状态 | 规则计算是否实际完成 | 未运行、运行中、完成、失败/部分完成 | 否；执行失败继续走执行门禁 |
| 业务 finding | 已执行规则所得业务结果 | `hit`、`miss`、`undecidable` | 是 |
| 范围限制 | 因可选来源缺失/不可用而未覆盖的规则集合 | 规则 ID、主体、来源角色和原因 | 否 |
| 报告就绪 | 当前代是否满足输出门槛 | 可预览、可正式生成、被真实待核事项阻断 | 否 |

## 来源状态语义

- `absent`：可选来源尚未提供；对依赖它的规则形成“本轮未纳入核查”的范围限制。
- `processing`：材料仍在既有解析流程中；保持既有运行中状态和报告就绪保护，不能当作缺失或成功。
- `unreadable`：解析已终态失败、没有可用页或必要页不可读；只限制依赖该来源的规则，披露原因，不将其静默等同于未提供。
- `unlinked_or_conflicted`：主体/材料归属无法确认或存在冲突；相关规则不消费该来源，保留独立归属问题及范围限制。多份材料只有在属于相互独立的总包且关系未明确时才阻断；同一总包的分册、附件或补充协议须经用户明确关联为来源集后才能一起消费，不能自动按文件名或时间合并。
- `available`：来源已归类、归属明确且需要的页面可读；按规则来源矩阵正常执行。
- 多份相互独立且关系未明确的总包仍按材料归属错误处理，不降级成普通范围提示；同一总包的分册、附件或补充协议可在明确关联后作为一个来源集处理。阶段 7.1a 已实现 task-scoped 来源集 ID、setup 阶段用户关联/解除 API、同事务审计和核查代快照；材料准入按完整且版本一致的来源集计为一个总包来源，独立或关系失效的多份总包仍阻断。改类或删除会解除关系并审计，材料替换不会自动继承关联，须由用户重新确认。服务端业务开关仍默认关闭，rollout 另行决策。

## 规则依赖矩阵

阶段 0 必须维护单一矩阵。每项规则至少记录：规则 ID/版本、适用主体、必需来源角色、可选上下文角色、证据类别/正反证、来源缺失策略、不可读/归属冲突策略、当前内核行为、期望行为、报告字段和测试夹具。

| 来源/情形 | 规则层处理 | 整体任务/报告影响 |
| --- | --- | --- |
| 规则自身必需来源缺失或事实证据不足 | 继续使用该规则既有 `undecidable` 语义 | 按既有真实待核门槛处理 |
| 仅缺少可选总包，且规则依赖总包 | 该规则标记 `not_covered_optional_source`；不生成 finding | 其他规则继续；范围限制本身不阻断正式报告 |
| 缺少总包，但规则不依赖总包 | 正常执行 | 不产生总包范围提示 |
| 总包解析仍在处理中 | 保持材料处理/执行状态 | 遵循既有运行中保护，不能提前确认报告 |
| 总包终态不可读、归属冲突或所需页缺失 | 仅限制受影响规则，保留具体来源问题 | 不得误报通过；按终态范围限制披露，不扩散到无关规则 |
| 多份独立总包且关系不明 | 材料归属/准入错误 | 阻止启动/继续，等待用户说明或更正 |
| 同一总包的分册、附件或补充协议 | 用户明确关联后视作一个来源集 | 汇总来源状态；任一必要组成文件处理中/不可用时，依来源状态规则处理 |

T15-01/02/03/05、W16-03、V16-02、条件开启的 A1 金额比例规则仅作为首轮审计候选，不在矩阵冻结前假设所有候选都应改为相同策略。

## 领域与 API 投影

`ScopeLimitation` 是独立于 `BsFinding` 的只读投影，最少包含：核查代/generation、规则 ID、主体 ID（如适用）、受限来源角色、来源状态、受限原因、展示文案键和产生时间。不得包含材料正文、模型提示词或凭据。投影应能按当前代重新计算/核验，历史代以其冻结快照读取。

阶段 1 已完成只读契约核查，并推荐复用 `BsTaskEvent` 的代际事件承载当前投影，在 `BsReviewVersion.snapshot_json.scope_coverage` 冻结历史；不新增数据库表。事件 payload 必须按版本化 schema 严格校验，事件缺失/重复/代际或指纹不匹配时不能返回空限制列表。

API 把 findings、scope limitations、rule execution coverage 和 report readiness 分开表达。不能只靠 finding 文案、自由文本或前端本地推断恢复范围限制。字段、状态、接口兼容和旧代规则详见 `domain-api-contract.md`；用户已于 2026-11-12 确认该契约并批准进入阶段 2，阶段 2–6 已通过代码与隔离验收，阶段 7.1 业务口径已确认。新增的多文件来源集关联能力须在 rollout 前补齐。

## 待处理工作区与人工动作

- 范围限制显示在待处理工作区的独立“范围提示”分区，和需要人工裁决的 finding 同屏但分组、计数、API 类型和操作不同。
- 不提供 finding 的采纳/忽略按钮；不写 review receipt；用户无需完成该提示才能处理真实 finding。
- 文案说明受限规则、缺少/不可用的来源及其影响；不得使用“符合”“不符合”“已核实”或笼统宣称“全部无法核查”。
- 提示与当前核查代材料状态同步。上传本身不清除提示；受影响规则在新代成功执行并确认覆盖后，当前代提示才解除。

## 报告与任务收口

- 所有正式报告入口、意见书、Word/PDF、证据包和 API 使用统一 readiness 计算与结构化阻断原因。
- `ScopeLimitation` 不进入 finding 结论统计，不触发 `undecidable` 人工处置门禁。
- 报告应列出未纳入本轮的规则/主体/来源原因，并明确结论范围；存在范围限制时不得标为完整覆盖或完整通过。
- 未完成/失败的必需核查仍按执行门禁阻止正式报告；真实 `undecidable` 仍按现有报告政策处理。
- 可选来源受限与一般材料缺件分栏呈现，避免“补一份总包可消若干必需材料缺口”这类错误关联。

## 补件与历史版本

1. 补件计划按来源角色和规则矩阵计算受影响规则；若不能确定影响范围，按既有策略扩大为全量重核。
2. 上传后依次确认解析终态、材料角色、主体关联和版本关系；只有这些前置条件成立才激活新核查代。
3. 新代对受影响规则重算；只有新代覆盖状态为完成且来源可用，才移除当前代对应范围限制。
4. 旧代 finding、范围限制、报告快照和人工意见不可改写。无关规则只能按既有证据继承策略携带，并显示来源代际。

## 与 MoMA AI 选页的边界

`bs-moma-ai-scope-selection` 负责选择器能否安全缩小 AI 输入，且不得改变固定规则 finding 和报告结论。本变更负责业务来源覆盖、规则执行状态和报告范围。T15-05 的 `general + labor` 只是其跨来源规则/选页证据覆盖要求，不等于任务级总包必传门槛。缺总包时：固定核查依据本规则矩阵决定是否将 T15-05 标为未覆盖；AI 选择器不得据不完整关系缩页，按其既有 fail-closed 契约保留 baseline。两个变更只通过规则覆盖和来源状态投影对接，不共享 rollout flag。

| 角色 | 主要责任 | 必须确认的阶段产物 |

| 后端/领域工程 | 实现来源状态、规则覆盖、finding、执行状态和报告就绪的分离及代际快照 | 阶段 1、2、5 的契约与纵向回归 |

| QA/审计 | 构造边界矩阵，核实门禁一致性、历史只读、主体隔离和可追溯性 | 阶段 0 测试矩阵；阶段 6 隔离验收记录 |

## 实施阶段

| 阶段 | 目标 | 关键交付 | 阶段验收门 |
| --- | --- | --- | --- |
| 0. 规则与状态冻结 | 把现状、确认原则和未知点落成逐规则矩阵 | 来源依赖矩阵、状态转移表、当前/期望差异 | 所有受影响规则有来源、缺源策略、报告映射和责任人；无“总包全部必需”的隐式假设 |
| 1. 领域/API 契约 | 独立表达范围限制、执行覆盖和报告就绪 | `domain-api-contract.md` 中 DTO/event/snapshot 投影及兼容方案 | 契约由用户验收；finding 保持三态；范围限制可追溯到规则/主体/核查代；历史投影可读 |
| 2. 固定规则垂直切片 | 逐规则将可选总包缺失与真实证据不足分开 | 来源矩阵驱动的规则内核行为和回归 | 无总包时无相关假 finding；依赖规则未覆盖；无关规则照常运行；必需材料缺口仍 undecidable |
| 3. 人工工作区 | 呈现独立中性范围提示 | API 与前端独立分区、无处置按钮 | finding 数量/状态/回执不因提示变化；材料变化后当前代投影正确 |
| 4. 报告与门禁 | 统一范围说明、意见结论和正式输出规则 | readiness 单一实现，报告/Word/PDF/证据包/API 一致 | 只有范围限制时不阻断；披露所有未覆盖项且不称完整通过；真实阻断仍有效 |
| 5. 补件新代 | 让来源补充真正闭合受影响核查 | 影响计划、新代重算、提示撤销、历史保留 | 上传不自动消提示；新代成功覆盖后解除；旧代证据与人工意见不变 |
| 6. 隔离端到端验收 | 验证规则到报告/补件闭环 | 隔离样本矩阵、API/UI/报告产物与验收记录 | 缺失/可读/不可读/错主体/冲突、无关规则、失败重试、旧新代全部通过；无共享数据写入 |
| 7. 业务验收与发布决策 | 由业务负责人确认结果口径 | 人工验收记录、独立发布/回滚决定 | 用户单独批准后才可启用/发布；盲审仍由用户另行决定 |

## 风险与控制

| 风险 | 控制 |
| --- | --- |
| 把 `not_covered` 映射成 `miss` 或 `undecidable` | 独立类型/投影；规则和报告计数回归断言 |
| 忽略材料处理尚未完成 | `processing` 与 `absent` 分开；沿用现有运行/报告门禁 |
| 只修 finding 文案，其他导出仍阻断 | 统一 readiness 并遍历所有输出入口 |
| 新代提示已消失但规则未成功执行 | 以新 generation 的规则 coverage 为唯一解除依据 |
| AI 选页和业务规则语义相互污染 | 独立 OpenSpec、状态类型和 feature flag；baseline fallback |
| 旧版本被新语义静默重算 | 历史快照只读；仅新核查代使用新契约 |
