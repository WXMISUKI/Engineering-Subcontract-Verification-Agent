# 独立版代码授权与交付方式：讨论稿

本文帮助权利人理解选项，不是法律意见，也不是已确认的授权或交付结论。用户已同意仓库暂时公开，并确认选择开源许可路线、不走商业许可；这两项决定并不自动决定本项目自身的具体许可证。下方其他方向仅作为比较背景，不作为当前实施方案。

## 先区分三件事

1. **本项目代码**：独立版和迁入代码的权利人，需要决定授予客户或公众哪些使用、修改和再分发权限。当前仓库没有项目自身的明确许可证；[GitHub 的说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)指出，公开仓库本身不等于授予一般性的开源许可。
2. **第三方软件**：PyMuPDF、ParadeDB、MySQL 等分别受其自身许可证约束。客户专用合同或本项目自选许可证，不能单方面取消这些既有条件。当前后端直接使用 PyMuPDF；独立知识数据库使用 ParadeDB 镜像。具体哪些自有代码与组件构成许可证意义上的组合、源码提供范围等，须结合实际集成与交付方式核实，不能仅凭 Docker 拆分作结论。
3. **知识资料和业务数据**：资料的复制和交付范围、合同材料及个人信息的处理，应另行按权利归属和客户约定确认。代码开源或向客户提供源码，并不自动代表应公开知识原件、客户业务文件、账号或密钥。

## 供权利人比较的方向

| 方向 | 客户能做什么 | 对当前项目的影响 |
| --- | --- | --- |
| 按适用开源许可证交付 | 按各项许可证使用、修改、再分发相应软件，并取得适用的源码及声明 | 与当前已选择的核查方向一致；需确认自有代码权利、适用的兼容许可证和完整对应源码，部分许可证允许下游再分发，不能只用合同单方面取消。公开代码本身不等于所有义务已经满足。 |
| 客户专用授权，同时满足第三方开源条件 | 客户对自有代码的权利由合同约定；第三方部分保留各自许可证授予的权利 | 是否能实现预期的保密或再分发限制，取决于实际组合及适用许可，不能假设所有代码都能闭源。PyMuPDF 权利人提供商业许可选项；如采用，需要核实覆盖本项目的使用和再分发，但这不替代其他组件的核查。 |
| 调整组件或取得其他商业授权后交付 | 根据最终合同与替代组件许可证约定 | 可能需要采购、替换组件、重建镜像并重新验证 PDF 处理、知识检索及离线恢复；目前没有授权执行这一方向。 |

AGPL 具体义务取决于实际软件、修改、分发和网络运行方式；[AGPL 原文](https://www.gnu.org/licenses/agpl-3.0.en.html)分别规定了分发和修改版本的远程网络交互情形。[PyMuPDF 官方许可说明](https://pymupdf.io/licensing)提供 AGPL 与商业许可两种路径。是否适合本项目应由权利人结合实际部署和合同确认，不能直接推断全部源码必须向公众开放，也不能保证客户专用合同可以覆盖全部第三方义务。

## 作决定前需要核实

- 谁拥有或有权许可原项目迁入代码、内部规则与六份知识资料，是否存在雇佣、客户合同或第三方约束。
- 客户是否需要源代码、是否可修改及向其他主体再分发，是否计划向其他客户交付；本次实际是 Docker 镜像和资料交付，并包含可联网的模型服务。
- 明确全部第三方组件版本、源码和通知材料；参见 `license-review.md`、`license-triage.md` 及源码说明（仓库中为 `third-party-source-notes.md`，候选包中为 `third-party-sources/README.md`）。当前仍有未核项，不能宣布正式交付已满足许可证。

待以上事实清楚后，由有权决定的人员选择项目授权并让专业人员确认适用条款；在此之前不自行添加项目 LICENSE、承诺闭源或宣称已完成合规。
