# 独立分包服务运维说明（候选，未完成离线交付验收）

## 范围与部署前提

该 Compose 仅部署工程分包及其基础服务。镜像和知识种子可离线提供，LLM、Embedding 以及扫描件识别服务仍须按环境配置并可访问。安装前核对 CPU 架构、磁盘、内存、模型接入、访问域名和 HTTPS；客户机器与资源需求尚未实测。

只运行一个 backend 实例和一个 worker。所有连接同一 `bs_review` 数据库的后端必须使用同一个支持 Linux `flock` 的上传卷；不同上传卷连接同一数据库不受此锁保护，不支持。运行中不得删除上传卷内 `.bs-backend.lock`，不得绕过独立 ASGI 入口。后端启动先获取锁，再把中断中的材料标为失败、把 `preparing` 任务恢复为 `setup`；已完成材料不会重置。运行者应在界面查看事件，按提示重新上传或重试。使用网络文件系统时须先验证其跨容器锁语义。

已登录的限流操作按签名有效、未过期的账号会话分别计数；登录接口仍按连接来源共享限制。由于前端反向代理会汇聚连接来源，多人集中登录可能共享登录额度，出现 429 时应稍后重试；不要直接信任客户端传入的来源地址头。

知识原件在 `delivery-data/knowledge-source/`，与清单名称、路径、SHA-256 一致；`delivery-data/knowledge-config/` 保存初始化日志、映射和查询密钥，必须限制访问。目录和 `.env` 不应提交 Git；业务数据库、上传文件及真实凭据不能包含在种子或镜像中。

保留一份未初始化的原始候选包，在另一份访问受限的副本中安装和运行。当前 Compose 会把运行副本中的 `delivery-data/knowledge-config/` 挂载给初始化容器并写入映射和查询密钥；运行时创建的 `.env` 也在该副本内。初始化后此目录已包含环境专属敏感配置，不能直接作为干净交付包转发或公开，备份应按冷备说明受控保存。`sha256sum -c` 只核对清单列出的文件，不会因目录里新增了 `.env` 或查询密钥而报错；再次分发前须使用未初始化的原始包并检查内容。

## 首次安装流程

在交付包目录执行，以下命令是候选操作流程，须在最终镜像及目标机器上复验。

在 Linux 目标机导入镜像前，从包根目录运行 `sha256sum -c SHA256SUMS`；必须全部显示 OK 且退出码为 0，缺文件或校验失败时停止安装并重新获取完整包。校验清单本身也要通过可信渠道核对，摘要校验只能检查内容与清单是否一致，不能单独证明发布者身份。当前候选镜像为 Linux amd64；其他架构不能据此认定兼容。该命令已在断外网 Linux 容器、候选目录只读挂载的条件下验证，未覆盖客户机器。

1. 从 `.env.example` 建立本机 `.env`，生成独立随机密码和密钥。`DATABASE_URL` 指向 `mysql` 容器的 `bs_review`，且连接密码与 `MYSQL_PASSWORD` 一致，特殊字符按 URL 编码。保管 `SECRET_KEY`、`KNOWLEDGE_AES_KEY` 等稳定密钥；AES 密钥必须为 32 字节，丢失后知识服务加密内容可能无法恢复。准备独立的新 WeKnora 管理账号及 Embedding 配置；本候选知识服务管理员密码须为 8 至 32 个字符且包含字母和数字，启用复杂密码策略时还须包含大小写字母、数字和允许的特殊字符。六份知识原件含扫描件，因此还需配置 `KNOWLEDGE_VLM_*`。模型地址只允许必要的精确可信域名，按需设置 `KNOWLEDGE_SSRF_WHITELIST_EXTRA`。业务模型和上传材料 OCR 分别使用 `LLM_*`、`OCR_CLOUD_*`。

   分包业务材料的 OCR、低质量重试、旋转及指定页补读均使用 `OCR_CLOUD_*` 配置的线上服务，不调用本地 OCR 模型；线上失败或配置缺失时保留未读和人工核实，不视为识别成功。为避免历史本地 OCR 缓存混入，当前业务 OCR 不读取旧识别缓存，重试和重复读取会产生新的线上调用与相应费用。电子 PDF 文字层仍直接提取。知识种子识别另由 `KNOWLEDGE_VLM_*` 配置，不能与业务 OCR 混同。
2. 在本机试用时使用仅监听 `127.0.0.1` 的 HTTP 入口并设置 `COOKIE_SECURE=false`；生产使用 HTTPS 反向代理并设置 `COOKIE_SECURE=true`。默认 secure Cookie 不会随普通 HTTP 请求发送。不要将测试用 HTTP 入口暴露给其他主机。
3. 准备好本地目录和离线镜像后启动基础服务：

   ```sh
   docker compose up -d --no-build --pull never --wait --wait-timeout 180 mysql knowledge-postgres knowledge-redis docreader weknora
   docker compose ps
   docker compose run --rm --no-deps --pull never backend python -m app.standalone.manage init-db
   docker compose run --rm --no-deps --pull never backend python -m app.standalone.manage create-user USERNAME
   ```

   `--wait` 等待带健康检查的服务通过检查、其他服务进入运行状态；若超时或失败，排查后再继续，不要直接执行初始化。需要 Docker Compose 支持这些选项；`--no-build` 是 `up` 的选项，`run` 不支持该选项，使用 `--pull never` 和已加载的镜像。建号命令在交互终端输入两次密码，密码不写命令行或聊天。`init-db` 创建缺失表，不是升级迁移工具，只用于新库或确认版本兼容的库。

   已用 Docker Compose 5.3.0 和隔离项目实际验证上述离线参数：启动独立 MySQL、执行 `init-db` 并创建合成账号均成功；建号使用非交互输入，未验证密码在交互终端中的隐藏显示，也未在此项测试中启动知识服务或验证完整初始化。临时项目和数据卷已清理。
4. 确认 WeKnora 健康、模型可用、源文件和外置密钥齐备，执行：

   ```sh
   docker compose --profile init run --rm --no-deps --pull never knowledge-init python -m app.standalone.knowledge_seed_cli --bootstrap
   ```

   `--no-deps` 不会自动启动或等待依赖，因此必须先确认第 3 步中的 WeKnora 和 MySQL 健康。命令只连接 Compose 内部 WeKnora 和独立 `bs_review`，创建新管理员、模型及分包知识库，等待解析、生成映射和受限查询凭据。受限凭据和模型的管理凭据分离。扫描资料通过外部 OCR/VLM 处理时，文件内容会发往所配置的服务。解析成功不代表业务依据和页码准确；上线前需核对五步召回和专家结论。
5. 启动应用并检查：

   ```sh
   docker compose up -d --no-build --pull never backend frontend
   docker compose ps
   ```

   等待前端代理及后端启动完成，访问入口对应的 `/api/health` 返回成功后再登录；启动窗口内可能短暂返回 502，`docker compose ps` 显示运行并不等于应用已就绪。然后登录测试账号，确认会话、任务创建、本人任务隔离与知识召回。健康接口只证明基础数据库连通，不代表模型、知识检索和业务结果均正常。

## 业主环境的模型配置

在业主环境单独建立受限的 `.env`，由业主提供对应服务的地址、模型和凭据；不要复制本机试用的 `.env`，也不要将凭据放入镜像、Git、交付包或聊天。配置前核对服务协议、网络连通性和允许访问的域名：

- 业务分析使用 `LLM_MODEL`、`LLM_API_BASE`、`LLM_API_KEY`；地址须符合现有 OpenAI 兼容客户端的接口约定。
- 业务材料线上识别使用 `OCR_CLOUD_MODEL`、`OCR_CLOUD_ENDPOINT`、`OCR_CLOUD_API_KEY`。`OCR_CLOUD_ENDPOINT` 是现有云 OCR 客户端使用的完整接口地址，并非业务模型的基础地址；更换服务商时还须确认请求和响应协议兼容，否则需要适配代码，不能保证仅修改地址即可使用。
- MoMA 业务文本与扫描页识别的配置、安全边界及尚未完成的验收，参见 [MoMA 适配配置与验收说明](../bs-moma-provider-adaptation/operator-guide.md)。该适配的本地模拟验证不代表已完成目标服务联通。
- 知识索引使用 `EMBEDDING_MODEL`、`EMBEDDING_API_BASE`、`EMBEDDING_API_KEY`、`EMBEDDING_DIMENSION`；扫描知识资料解析另用 `KNOWLEDGE_VLM_MODEL`、`KNOWLEDGE_VLM_API_BASE`、`KNOWLEDGE_VLM_API_KEY`。按实际网络配置精确域名白名单。索引模型和扫描解析模型分别核实，不能直接假定与业务 OCR 相同。

已有知识库更换 Embedding 模型或维度时，不应直接沿用旧向量索引：先备份并制定迁移方案，在隔离的新知识库中重新导入、建立索引并验证召回，再受控切换绑定。业务密钥、数据库密码和知识服务稳定加密密钥各自独立管理；不要在排障时公开包含密钥的完整 Compose 配置。

## 中断与重复执行

初始化会先记录待确认操作，再请求知识服务；已明确完成的步骤可重复执行。资料上传发生响应丢失后，确认没有其他初始化进程或人员修改该独立知识库，再用原参数重新执行 `--bootstrap`：程序核对管理员和模型配置、已确认的目标库及完整文件列表，只在同名候选唯一、库与模型一致、解析完成且下载的远端原件 SHA-256 与种子一致时自动恢复日志。下载只在内存中计算摘要，不写入原件或将内容写日志；该步骤需要管理员对原件的读取权限。若文件仍在解析，可待其完成后重试。列表不完整、权限不足、重复、原件不符或配置变化均保持停止；不得自行删除 pending 后盲目重试。该能力仅覆盖文档上传，其他未知操作仍需维护人员先备份配置目录及相关数据库、核对远端后处理。查询密钥创建若结果未知，不能从日志取回原始密钥，需单独处理已创建凭据并验证最小权限。

初始化锁异常残留时，必须先确认没有运行中的初始化容器，再备份锁和日志并核对中断状态；不能因看到锁文件就删除后重试。后端锁是另一种运行期文件锁，正常进程退出会释放文件锁，文件本身应保留。

### 管理员排查清单

以下仅用于定位问题，不授权修改远端对象或手工更改日志。先确认正在处理的是本次独立部署的 Compose 项目、独立 WeKnora 和独立业务库；确认没有初始化容器及其他运维人员并发操作，再按冷备说明保存同一时间点的配置目录和相关数据。主机上的 `delivery-data/knowledge-config/setup-journal.json` 记录 `operations`，其中 `pending` 表示请求结果不确定，并不表示远端一定没有创建。该目录还可能包含 `query-key`，备份和排查应限制访问，不要把配置目录、日志或密钥发到聊天或公开工单。

| 日志操作或现象 | 先核对什么 | 当前处理边界 |
| --- | --- | --- |
| `document:<SHA-256>` 为唯一 pending | 原种子、原参数、目标库、解析状态和管理员原件读取权限 | 满足上文条件时可原参数重试，由程序核验后恢复；否则保持停止。 |
| `administrator` | 在目标独立服务核对管理员是否已创建及原账号能否登录 | 仅用户名或邮箱相同不足以证明是本次操作；尚无自动认领，交维护人员处理。 |
| `embedding-model`、`vision-model` | 核对目标独立服务中模型身份、类型、地址及维度等配置 | 同名不等于本次创建；尚无自动认领，交维护人员处理。 |
| `kb:<集合>` | 核对独立空间、库名称、模型和视觉配置，以及是否有多个候选 | 现有日志没有创建操作的唯一标识，同名同配置也不能自动认领；交维护人员处理。 |
| `query-key` | 核对受限授权范围、远端凭据状态及本地 `query-key` 是否完整存在；不得显示或传播密钥 | 创建响应或本地写入中断时，不能凭存在文件或同范围推断二者必然对应；需维护人员制定凭据处置与验证方案。 |
| 配置指纹项 pending、多个 pending、日志损坏或状态不一致 | 保留原日志、配置和备份，核查异常发生前后的操作与环境 | 不手动改状态、不清空目录、不重复创建；由维护人员分析后选择可验证的修复方式。 |
| 日志已完成但解析未完成、失败或映射未发布 | 区分等待解析、解析失败、受限凭据和绑定发布阶段，检查独立服务状态 | 解析仍在进行可按原配置稍后重试；失败或绑定不一致先排查，不把部分映射当作交付完成。 |

上述人工情形目前没有通用的一键恢复命令；修复需根据备份和实际远端状态单独制定并验证。不得直接删除 pending、凭据、库或数据卷，也不得将源项目知识库当作排查目标。

## 升级和备份边界

业务 MySQL、上传卷、WeKnora PostgreSQL、知识文件卷、知识原件、知识映射和查询密钥、以及稳定加密密钥应作为相互关联的一致备份集保存。维护窗口内停止写入并确认无初始化或解析任务后备份，分别校验和保存；恢复只在隔离的新环境进行，不覆盖现存数据。Redis 和临时目录是否可重建须随对应 WeKnora 版本确认。操作草案见 `cold-backup-recovery-draft.md`；下述隔离演练提供部分证据，但不能推断客户环境和全部业务场景均可灾难恢复。

隔离合成演练已验证一种冷备方式：停止 Compose 服务，在只读挂载的数据卷上用 `tar` 归档 `bs-mysql`、`bs-uploads`、`knowledge-postgres`、`knowledge-files` 和 `knowledge-redis`，在另一套确认空置的卷中以 root 保留归档所有权解包，再用相同镜像版本和稳定密钥启动。恢复后核对了业务账号和任务、知识管理员登录、PostgreSQL 测试记录及上传和知识文件。

另一次知识服务演练将合成文本索引后，冷备并恢复知识数据库、知识文件、Redis、受限查询凭据及稳定密钥，在恢复环境中通过原凭据再次检索到同一文件。之后还在隔离环境将六份知识资料、业务库绑定、映射和凭据作为同一备份集恢复，五步各抽查一项在恢复前后均命中目标文件；其中第二步没有可靠页码。Embedding 服务仍需可访问；全部规则、目标环境和专家业务结果尚未验收，不能将这几项抽查视为完整灾备验收。

当前没有版本化数据库迁移机制。升级前必须核对应用及 WeKnora 的版本变更、数据库迁移要求和完整备份，在隔离副本验证迁移与回退；禁止把 `create_all` 当作现有表升级。正式版本及迁移方案确定后再执行升级。
