# 设计：负面清单辅助候选相关性门控

## 观察到的问题

当前候选规划会为每个主体枚举全部负面清单条目，并把同一组范围标题摘录提供给每条规则。通用校验只验证材料引文、规则依据的来源身份和连续原文，不验证材料引文含有当前规则的工程信号。于是同一段通用文字可分别通过不同规则的出处校验并落成多个无法核实 finding。

## 决定

- 用 `negative_list_matchers.json` 中每个条目的 `triggers` 与可选 `context` 作为**候选召回信号**。触发信号只决定是否值得辅助核查，不证明违反规则。
- 候选 planner 只把同一规则、主体下包含触发词及所需上下文的可读范围摘录交给模型；没有规则信号的规则保留 `not_run` 和明确原因，不生成材料 finding。
- 通过人工复核队列的每条材料引文自身必须包含该规则的触发信号；配置 `context` 的规则要求同一引文满足上下文。不得用页面其他位置的触发词替无关引文背书。
- 阈值规则无需先抽出阈值才能进入候选。出现规则工程信号但数值缺失时仍允许 `undecidable` 建议，交人工核实。
- 不跨规则按 quote 去重。同一事实只有在分别满足每条规则自己的触发信号与上下文时，才可成为多个规则的人工核实候选。
- 固定规则的 `hit/miss/undecidable` 仍由完整确定性核查链产生。AI 候选不增加 `W16-02` 的已评估条数；无触发信号表示未由本辅助链评估，不等于未命中。
- 引文/候选契约变化使用候选专属版本号。旧候选事件保持历史记录但不再作为当前建议或缓存结果复用；重算须由用户显式重试触发。

## 角色核验

- 规则审核：触发词只用于召回，阈值证据缺失仍须保留人工核实路径；上下文约束必须与触发词同时成立。
- 证据审核：证明“原文存在”和证明“原文与规则相关”是两项独立校验；相关性必须在本条 quote 上成立。
- 运行审核：部分批次状态继续保持 partial；旧候选版本不能隐式重放或触发新的模型调用。
- 报告审核：候选只作辅助人工待办；固定规则的覆盖状态及报告门禁不因候选过滤而被抬高。

## 验收重点

- 两组通用范围/价款原文不能通过 `NL-B-01..12` 或 `NL-T-01..08` 的不相关证据校验。
- 触发词与上下文同时出现在同一材料引文时，候选继续可用。
- 规则信号存在但阈值缺失时允许 `undecidable`；不能因缺阈值误当未命中。
- 无规则信号的候选为未运行/未评估，不生成 finding，不增加确定性覆盖数。
- 部分批次仍为 partial；旧候选版本只要求显式重试，不影响其他 AI 核查组的版本。

## 2026-11-13 材料质量缺口与调度口径

真实材料只读核对发现，可疑页既包括人员证件、名单，也包括合同签署页和包含工程内容的清单（第 63、64 页）。因此不能按整份报审材料的角色排除可疑页，也不能以 OCR 输出长度证明读取完整。

核对摘要（物理页码，不记录个人信息或合同原文）：20、26、31、35、37、39、43 为人员证件组合页；21 为横置安全证书；28 为横置人员名单；61 为合同签署信息；63、64 为横置工程量清单。20、26、31、35、37、43 的正文计数分别为 19、3、5、0、0、7，原页均有实际内容；39、61、64 的 OCR 原始字符串很长但大量为结构标记；28、63 的表格结构存在缺失风险。上述页均应保持质量待核，不能仅据字符数判定。

本次只读状态核验：task 4 仍为 running，12 页仍为可疑；20 条候选为无信号且来源读取不完整。旋转重试页为 3、5、36、38、40、42、44，其中 3、5、36、42、44 有旋转恢复记录；该集合与上述可疑页不同。现有读取确认逻辑可消费事件式记录，但代码检索尚未发现生产写入确认入口；定向云 OCR 接口当前未启用，且补读结果仍须人工核对。

用户确认：存在真实材料读取缺口时，继续运行能够独立执行的其他核查组；受影响项目保持未覆盖，提供可定位原页的人工核对路径。全部组处理后，人工复核完成可生成范围受限报告，报告必须明确列出未覆盖规则和物理页码，不能称完整通过，不能将缺口记作未命中、通过或已人工确认。不可核实的技术错误和上下文变化仍立即中止，不得笼统吞掉异常。

### 2026-11-15 执行状态与覆盖状态分离

新建任务的真实事件证明：五个 AI 组均已进入终态，A1 有 20 条候选因读取缺口未运行，但后台把受控的材料范围结果写成 `check.ai_background_failed`。这使 UI 显示“核查已中断/重试”，与“全部组已执行、覆盖待人工复核”的事实不符，并可能诱导同一材料重复调用模型。

- 所有配置组终态且唯一阻断为已定位的材料读取缺口时，后台记录 `check.ai_background_review_required`，投影 `state=review_required`；覆盖仍为不完整，报告/任务收口门禁不放宽。
- 真实模型/服务失败、未知未运行、租约或覆盖不一致仍保持 failed / fail-closed，并保留显式重试。
- 对已记录的旧 `incomplete_material_scope` failed 事件，仅在实时覆盖再次证明组均终态且 gap 可归属时投影为 review_required；原事件不改写。证据失配时保持不可核实或失败。
- review_required generation 不接受同代后台 retry；更新材料或重跑核查会形成新 generation，按现有指纹和显式重跑规则执行。
- UI 显示“核查待人工复核”、说明缺口使相关规则未形成覆盖结论，并提供进入人工复核入口；不显示执行失败或同代重试按钮。

### 2026-11-17 字面召回与语义候选并行

用户确认采用混合方案：确定性规则/触发词筛查先运行；工程范围可读但没有字面触发词的规则，进入受来源约束的 AI 语义候选筛查。该筛查是候选召回，不产生负面清单命中、未命中或合规结论。

- 对每个已确认主体枚举当前规则快照中的适用规则。字面触发词仅作高精度召回，不再作为语义候选唯一入口。
- 语义候选仅使用当前核查代中可读、同主体的工程范围片段及精确冻结规则原文；请求受现有 `max_batches`/用量记账/并发租约控制。超预算、服务失败或响应不完整保留为执行未完成，不伪装成“无候选”。
- 模型提出候选后，材料引文必须精确回指原材料、主体、页码和原文片段；规则引文必须精确来自冻结依据。语义候选仍标记为人工提示，不能进入机器结论或固定规则覆盖统计。
- “筛查完成、未提出候选”只说明候选模型没有提出人工线索，不等于逐条规则确定未命中。报告可以披露筛查范围和限制，不得据此生成符合/不符合。
- 当前 `source_reading_complete` 是整份分包合同级布尔值，任何可疑页都会影响全部无信号规则。新增按规则记录的范围覆盖事实：规则候选对应的工程范围材料/物理页、读取状态、精确未读页及归属依据。只有可疑页可追溯到相关范围片段时才影响对应规则；无法归属时记录独立的未归属范围缺口，不伪称所有规则均因该页未评估，也不将其作为已完成筛查。
- 未读/OCR 存疑页不送入语义模型；可读范围仍可筛查其他候选。受影响规则保持未评估并可定位原页；只有规则-页面映射完整且其他门禁通过时才允许范围受限结果，禁止把未知失败按 OCR 缺口降级。
- 新筛查方式、输出 schema、证据校验和页面归属投影必须提升负面候选 validation version；历史事件/回执保持原状，新筛查须显式重试。

实现验收应覆盖：字面触发候选、语义等价但无触发词、普通同主题文本误召回、相关范围 OCR 缺口、无关页 OCR 缺口、无法归属的缺口、预算耗尽、模型部分失败、旧版本缓存、引用错页/错主体，以及候选无结果不等于规则未命中。所有模型行为均以 mock/离线测试验收；真实 Provider 或真实业务调用另行授权。

### 验收场景

- A1 因材料范围缺口未执行候选时，A2 和内部记录继续执行；最终 job 保留未完成及缺口原因，人工复核后仅可生成披露未覆盖规则、材料和页码的范围受限报告。
- 其他组的未知失败、租约未结束、规则或材料指纹变化不被当作范围缺口跳过。
- 用户可定位到材料及具体可疑页进行人工核对；查看本身不改变读取状态，不得将未读取的内容视为已评估。
- 缺口处理前后均保留历史事件；重试只运行有权限且当前上下文有效的项目，避免重复模型调用。
- AI 运行未结束、规则或材料指纹不一致、未知失败或无法准确列出受影响规则和页码时，不得使用范围受限路径。报告页面和所有导出格式必须一致披露，正式结论只能覆盖已评估范围。
